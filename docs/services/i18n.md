# Traducciones y locales

La traducción gettext de SimpleRest vive en el paquete separado `boctulus/simplerest-i18n`. Sus catálogos son datos de la aplicación bajo `LOCALE_PATH`, que por defecto apunta a `app/Locale/`. El `composer.json` del core no declara ese paquete como dependencia; el autoload disponible en un checkout no demuestra que una instalación consumidora lo incluya.

## Seleccionar idioma y dominio

El autoload del paquete declara dos helpers globales: `setLang(?string $lang)` y `trans(string $text, $domain = null)`. La clase `Translate` ofrece las operaciones de locale y dominio:

```php
use Boctulus\Simplerest\Core\Libs\i18n\Translate;

setLang('es_AR');
Translate::bind('messages');
echo trans('Welcome');
```

`setLang()` normaliza guiones, mayúsculas y sufijos de encoding; selecciona un locale existente y no cambia el idioma si no encuentra uno compatible. `bind($domain, $path)` registra la ruta del catálogo y selecciona el dominio actual. Si el msgid no tiene traducción cargada, `trans()` devuelve el propio msgid.

El idioma actual, el dominio y los catálogos viven en propiedades estáticas. En un proceso persistente, define cómo aislar o reinicializar ese estado entre peticiones.

## Archivos y fallback

El loader recorre directorios de locale bajo la ruta enlazada y carga catálogos `.po` en `LC_MESSAGES/<dominio>.po` mediante `POParser`. El locale predeterminado para fallback es `en_US`. Si existe también un catálogo base de idioma —por ejemplo `es/` junto a `es_AR/`— la cadena combina fallback, idioma base y variante regional; la variante puede reemplazar traducciones anteriores. Si no existe el catálogo base, conserva la ruta regional como catálogo completo y no añade automáticamente el idioma base.

`Translate::useGettext(true)` opta por la extensión gettext de PHP cuando está disponible. No se activa automáticamente. Con gettext habilitado y sin un catálogo compuesto por idioma base y región, `bind()` usa `bindtextdomain()`; en el caso compuesto usa el parser `.po`. La extensión gettext y la disposición de catálogos afectan qué rama se usa.

## API complementaria

- `Translate::setFallbackLocale()` cambia el fallback.
- `Translate::getLocale()`, `getLocaleChain()` y `getDomain()` consultan el estado actual.
- `Translate::exportLangDef()` genera archivos `.po` y puede invocar `msgfmt` para escribir `.mo`.
- `Translate::convertPot()` crea o actualiza catálogos PHP a partir de archivos `*.pot.php`.
- `LangDetector::langs()`, `is()` y `detect()` ofrecen una heurística basada en palabras para inglés, español, italiano, hindi y bengalí. No está conectada automáticamente con `setLang()` ni con la negociación HTTP.

Las operaciones de exportación pueden escribir archivos y no se ejecutaron en esta auditoría. El paquete expone `setLang()` y `trans()` como helpers globales; no hay otros helpers de traducción definidos en el archivo de autoload inspeccionado.

## Plurales y límites

`Translate::transChoice()` consulta una propiedad estática `pluralForms`, pero el loader de dominio no la rellena a partir de los catálogos. El parser `.po` contempla entradas plurales, aunque esa ruta no quedó demostrada de extremo a extremo; no asumas que `msgid_plural` queda listo para `transChoice()` al hacer `bind()`.

`Validator` enlaza el dominio `validator` al construirse y usa `trans()` para mensajes. Esa integración implica el paquete de traducción; la dependencia no aparece en el `composer.json` del core. Registra esta diferencia como límite de distribución, y no como prueba de que una instalación limpia ya la resuelve.

Hay tests de traducción y de convergencia de catálogos en `unit-tests/translator/`; se inspeccionaron, pero no se ejecutaron. No se cambió el locale del proceso ni se generó o compiló un catálogo durante la revisión.
