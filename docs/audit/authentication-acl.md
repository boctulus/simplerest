# Authentication and ACL claim ledger

This ledger records significant claims from the legacy split pages and archived monolith against the current source. The old pages remain unchanged as provenance; they are not canonical documentation. There is no root-level DOC.txt in this checkout; the archived monolith examined here is docs/framework/_archive/DOC-Simplerest.txt. The current source trace is not a runtime or end-to-end verification.

## Authentication claims

| Claim / finding | State | Evidence and boundary |
| --- | --- | --- |
| Authentication is handled by a general auth middleware on every request. | Rejected | <code>front_behaviors.auth</code> is <code>AuthHandler</code>, which resolves <code>/auth</code> actions. The built-in API resource path calls <code>IAuth::check()</code> from <code>ResourceController</code>; the default FrontController invokes the action before its middleware handler. Ordinary web controllers have no automatic credential check. |
| JWT and API-key credentials are detected. | Verified | <code>Request::getAuth()</code> accepts <code>Authorization</code> or the <code>token</code> query parameter; <code>getApiKey()</code> accepts <code>X-API-KEY</code> or <code>api_key</code>; <code>authMethod()</code> selects API key before JWT. <code>isAuthenticated()</code> only reports credential presence, not validity. |
| Missing credentials always return 401. | Rejected | <code>AuthController::check()</code> assigns the configured guest role with null UID and empty user permissions when neither credential is present. Access then depends on guest ACL rules. |
| Successful login issues access and refresh JWTs. | Verified | <code>AuthController::login()</code> calls <code>gen_jwt()</code> twice with separate token settings. The access payload contains role/permission data; the refresh payload contains UID plus common JWT metadata. Existing auth test source exercises login and renewal, but was not run. |
| An expired access token refreshes automatically. | Rejected | <code>jwtPayload()</code> rejects invalid/expired access tokens with 401. Renewal is a separate <code>token()</code> action using the refresh-token secret. |
| <code>/auth/{action}</code> is the default API route, and each listed action is available at both <code>/auth/*</code> and <code>/api/v1/auth/*</code>. | Partial | With the current <code>remove_api_slug=false</code> setting, <code>RequestHandler</code> recognizes <code>/api/{version}/auth/{action}</code>. When the option is enabled it shifts the route prefix. The unversioned GET <code>/auth/login</code> and <code>/auth/rememberme</code> entries in <code>config/routes/auth.php</code> are web pages. The legacy endpoint table is not valid as an unconditional API route contract. |
| Login field names such as <code>users_password_field</code> and <code>users_email_field</code> are configurable in <code>config.php</code>. | Rejected | Current config names <code>users_table</code>; <code>AuthController</code> obtains user field names from the configured user model. Those legacy field keys are not present in <code>config/config.php</code>. |
| <code>auth()::getCurrentUserId()</code>, <code>getCurrentUser()</code>, and <code>Request::bearerToken()</code> are framework APIs. | Rejected | <code>IAuth</code> exposes <code>uid()</code>, <code>getRoles()</code>, and <code>getPermissions()</code>; the core Request exposes <code>getAuth()</code> and credential-detection methods. No matching methods exist in the core contract/source. |
| Password-reset <code>pwdv</code>, a 32-character distinct email-token secret, and no session issuance are generic framework behavior. | Application-specific | The current app's <code>MyAuthController</code> overrides reset methods and contains the <code>pwdv</code> and secret checks. Core <code>AuthController</code> has separate reset methods and does not establish that application policy as a generic contract. <code>PasswordResetTest.php</code> covers the app override in test source only. |
| The password-reset security changelog proves the entire reset and mail overhaul is complete and verified. | Partial | The current app override contains the described <code>pwdv</code> path, but this phase did not verify mail delivery, the changelog's Mail.php claims, dependency restoration, SMTP, or the reported PHPUnit result. The changelog is an application-era record; its end-to-end and test claims remain unverified here. |
| Google and Facebook OAuth are built-in auth providers. | Application-specific | The current application has provider configuration/controllers. The core <code>IAuth</code>/<code>AuthController</code> path establishes JWT and API-key checks, not a framework OAuth flow. |
| The Xeni authentication notes describe SimpleRest's authentication contract. | Application-specific | <code>app/Modules/Xeni/docs/api_authorization.md</code> concerns an external provider integration. Its recorded request outcomes were not reproduced or treated as evidence of core behavior. |
| The archived monolithic guide is a current auth/ACL specification. | Historical | The archived <code>DOC-Simplerest.txt</code> is retained as evidence of earlier examples, including its OAuth2-style label and version-specific controller examples. Those examples do not define current core behavior. |
| Token values shown in the legacy page represent a short-lived access token and a roughly ten-year refresh token. | Partial | The refresh lifetime expression is 315,360,000 seconds; the current access lifetime expression is <code>60 * 15 * 50000</code> seconds (45,000,000 seconds). The old “short-term” description is contradicted by the current source value. No effective runtime config was inspected. |
| Login failures, invalid tokens, and access denials have known HTTP statuses. | Verified | Source calls the error response with 401 for incorrect login credentials, invalid API keys, and invalid/expired JWTs; selected inactive-account and callable-denial paths use 403. Response bodies and a live server were not verified. |

## ACL and automatic API claims

| Claim / finding | State | Evidence and boundary |
| --- | --- | --- |
| ACL is unusually sophisticated compared with Laravel packages. | Rejected | This is an unmeasured product comparison, not an implementation contract. Keep it historical only. |
| The core ACL has resource and special permissions. | Verified | <code>Core\Security\Acl</code> declares resource actions and special capability names; <code>AclEngine</code> evaluates them against a snapshot and request context. |
| Roles inherit from other roles. | Partial | <code>addInherit()</code> records a parent and copies the parent's current permission arrays; <code>RoleHierarchyService</code> uses recorded lineage for role-comparison operations. The source does not support treating every permission read as a fresh database hierarchy lookup. |
| Generic row-level and attribute-level ACL rules are implemented. | Rejected | The core engine resolves resource/action and special capabilities. Owner scoping and folder checks exist in separate API/folder paths; <code>AclContext</code> row/folder fields do not establish generic field- or row-policy evaluation. |
| BasicACL and FineGrainedACL are built-in modes selected automatically by core. | Partial | Both optional package directories exist. <code>Factory::acl()</code> includes the application's <code>config/acl.php</code>; this checkout explicitly imports FineGrainedACL. The core factory does not auto-discover a tier. |
| All roles and permissions are dynamically loaded from database tables. | Partial | Auth login/API-key paths load role assignments and user permission rows; JWT checks use role/permission claims in the token, with a role-field mapping when configured. ACL rule declarations come from the app config. FineGrainedACL adds database-backed user denies. Effective DB contents/runtime freshness were not checked. |
| The serialized ACL file is always used as a runtime cache. | Partial | The current app config writes a serialized object but sets <code>$acl_cache</code> to false, so this config rebuilds rather than restores the cached object. This is application configuration, not a core cache guarantee. |
| ACL rules are persisted to database and regenerated automatically as a universal framework behavior. | Partial | The optional FineGrainedACL package reads role and special-permission catalogs from DB, while the current app config builds declarations and writes a serialized file. The active config sets cache restore false; this does not establish universal persistence, automatic regeneration, or effective DB policy for other apps. |
| Every API action passes through ACL before controller/action execution. | Partial | Built-in <code>ResourceController</code>/<code>ApiController</code> performs credential and permission setup during construction; FrontController compares the API method against the callable list before calling that action. Construction has already happened. Auth actions skip the callable gate, and normal web controllers are not globally guarded. |
| Unauthenticated requests are denied while authenticated requests are authorized by role. | Rejected | Missing credentials become the guest role. Guest permissions depend on configured ACL rules; authenticated credentials are not sufficient by themselves to authorize an action. |
| Automatic CRUD uses table resource permissions, ownership scope, and global capabilities. | Partial | <code>ApiController</code> maps resource actions to ACL callables and has separate default owner-scope logic. Special <code>read_all</code>/<code>write_all</code> capabilities are implemented. This source trace does not establish every automatic endpoint or a successful end-to-end request. |
| ACL is API-version-specific through versioned controller directories. | Rejected for the built-in ACL path | <code>ApiHandler</code> retains a validated version and resolves the class from the resource slug. <code>ApiController</code> keys resource permissions by table name; there is no version key in the ACL call. A custom controller may branch on the global version. |
| ACL has implicit allow, wildcard, or fallback permissions. | Partial | The engine returns false when no matching grant applies. Explicit <code>read_all</code>/<code>write_all</code> expand to cross-resource action buckets. A literal <code>*</code> resource grant is recognized in the compiled generic permission path but not by <code>hasResourcePermission()</code> in the same way. No test establishes literal-star rules as an intended contract. |
| A user table-permission grant maps POST to <code>get</code> and PATCH to <code>putch</code>. | Partial; intent unresolved | These strings originate in the bitmask branch of <code>ApiController::__construct()</code>. <code>ApiHandler</code> dispatches the methods as <code>post</code> and <code>patch</code>; FrontController uses exact string membership. When no other rule adds the matching method, the ACL-added string does not match dispatch. The old spelling is present from the 2020 history, but no rationale, caller, or test asserting it was found. |
| HTTP method override and ACL selection use the same method. | Unverified; intent unresolved | <code>ApiHandler</code> dispatches <code>Request::method()</code>, which can apply URL/header overrides. <code>ApiController</code> selects its ACL branch from raw <code>$_SERVER['REQUEST_METHOD']</code>. No focused test or runtime probe establishes the result when they differ. |
| The current guest role is a safe default with no access. | Application-specific | This checkout's <code>config/acl.php</code> declares <code>read_all</code> and <code>write_all</code> for <code>guest</code>. The selected FineGrainedACL implementation validates capability names from the database. Effective runtime grants depend on DB state and were not probed; this is not a standalone default. |
| Every ACL permission source follows the total precedence <code>DENY &gt; USER_GRANT &gt; ROLE_GRANT</code>. | Partial | The legacy <code>AclCommands.md</code> states this universal order. In the compiled source, role allows are aggregated, per-user special allows are additive, a per-user table bitmask replaces the role-derived grants for that resource, and explicit denies are checked before allows. Deny wins for the matching permission, but the grant layers do not have one universal total order. Engine deny tests exist but were not run; CLI <code>explain</code> output was not executed. |
| Guests should receive resource-level <code>read_all</code> and all other roles should derive from guest. | Historical | This is advice in the legacy ACL guide, not a framework default or verified policy requirement. The current app instead declares global special <code>read_all</code>/<code>write_all</code> for guest; their effective behavior depends on the selected ACL integration and database catalog. |
| The ACL command guide's 23-command inventory, aliases, flags, dry-run behavior, and safety descriptions are current. | Unverified | <code>docs/framework/commands/AclCommands.md</code> is a legacy guide. The CLI command implementation and every documented invocation were not audited or executed in this authentication/ACL pass; retain them for the CLI audit rather than presenting them as canonical here. |
