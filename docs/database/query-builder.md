# Query Builder

This reference describes the current source paths and separates them from executed database behavior. No database query or PHPUnit case was run for this audit; the call shapes below are not a reproduced application workflow.

## Entry point

[`DB::table($from, $alias = null, $connect = true)`](../../src/framework/Libs/DB.php#L750) has two paths. For a table name it resolves an application model with `get_model_name()` and constructs that model. If `$from` contains ` FROM `, it instead constructs `MyModel` and calls `fromRaw()`.

The default `$connect` value is `true`. The [base `Model`](../../src/framework/Model.php#L14) uses [`QueryBuilderTrait`](../../src/framework/Traits/QueryBuilderTrait.php#L21); its constructor calls `connect()` when requested, which selects the current PDO connection. A table name therefore depends on the app's model/schema mapping and configured database connection. Direct construction of `Model` defaults to `$connect = false`; this differs from `DB::table()`'s default.

## Building and executing a read

The source-level call shapes below are implemented by [`select()`](../../src/framework/Traits/QueryBuilderTrait.php#L945) and [`where()`](../../src/framework/Traits/QueryBuilderTrait.php#L2649):

- `select('id', 'name')`, `select(['id', 'name'])`, and a comma-separated string are normalized into a field list.
- `where('id', 7)` and `where('id', '>', 2)` are converted to conditions. The method also accepts its array condition form.
- [`toSql()`](../../src/framework/Traits/QueryBuilderTrait.php#L1141) builds the SQL and records the precompiled SQL and bindings. It does not execute the query.
- On the ordinary, non-connected-table read path, [`get()`](../../src/framework/Traits/QueryBuilderTrait.php#L1877) builds SQL, prepares a PDO statement, binds values, and executes it when the model's `$exec` flag is true. On an executed read it returns fetched rows; with execution disabled it returns `false`.

[`dontExec()`](../../src/framework/Traits/QueryBuilderTrait.php#L386) disables statement preparation/execution in the builder path, but it does not make the standard `DB::table(...)->get()` flow offline. `DB::table()` connects by default, and `get()` reaches [`bind()`](../../src/framework/Traits/QueryBuilderTrait.php#L1566), which connects if the model has no PDO handle before it checks `$exec`.

When the model schema contains `deleted_at`, query construction adds `deleted_at IS NULL` unless deleted rows have been enabled with `deleted()`. The condition is generated by [`whereFormedQuery()`](../../src/framework/Traits/QueryBuilderTrait.php#L1439); its scope depends on the active model schema.

## Observed result edge case

On the executed path, [`first()`](../../src/framework/Traits/QueryBuilderTrait.php#L1928) fetches one row. When the fetch is empty, the current source returns `[]`, not `null`. This behavior has not been exercised against a live database and is recorded as an implementation inconsistency.

## Write-mode safety finding

`preview()` and `simulate()` are not a universal no-write guarantee. The source has mode checks in [`create()`](../../src/framework/Traits/QueryBuilderTrait.php#L3527) and the insert execution path, but [`update()`](../../src/framework/Traits/QueryBuilderTrait.php#L3055) and [`delete()`](../../src/framework/Traits/QueryBuilderTrait.php#L3293) execute when `$exec` is true without checking the selected execution mode. The legacy `preview()->update(...)` example is therefore rejected as unsafe. This anomaly is recorded for separate implementation investigation; no framework code was changed.

## Building conditions and SQL

Scalar conditions supplied through `where()` add placeholders and values for the builder's binding path. The method accepts an array condition, `(field, value)`, or `(field, operator, value)`; `orWhere()`, `whereOr()`, `orWhereLike()`, and the closure-based `group()`, `and()`, `or()`, `not()`, and related methods build grouped conditions. `whereNull()`, `whereNotNull()`, `whereNot()`, `whereLike()`, `whereDate()`, `whereBetween()`, and `whereNotBetween()` are convenience methods. Their emitted SQL can vary with schema and driver and was not executed here.

**Do not treat `whereIn()` or `whereNotIn()` as PDO-bound input.** Their array branch joins values into the SQL predicate; string values are wrapped in quotes without an escaping or placeholder step in that path. This source-level security risk is recorded in the [claim-level audit](../audit/README.md#claim-level-findings-query-builder). Keep those methods away from untrusted values until the implementation is reviewed. This warning also applies when the same array condition form is passed to `where()`.

`whereRaw()`, `orWhereRaw()`, `selectRaw()`, `havingRaw()`, `joinRaw()`, and `fromRaw()` accept SQL text. Some accept a separate values argument for placeholders; raw SQL fragments themselves are not transformed into safe expressions. Do not interpolate untrusted values into a raw string. `orHavingRaw()` is currently a stub: its method body is commented out and it returns no builder value. It is not a working API in this checkout.

`getBindings()` exposes the builder's collected values. `toSql()` compiles the query without executing it. The static `query($raw_sql, ...)` method is a separate raw SQL path; it should not be confused with the fluent query compiler.

## Selection, joins, ordering, and grouping

`select()` accepts a field list, an array, or comma-separated string; `addSelect()` appends one field and `selectRaw()` adds a raw projection. `distinct()` can add distinct fields. `join()`, `leftJoin()`, `rightJoin()`, `crossJoin()`, `naturalJoin()`, and `joinRaw()` cover the declared join forms. `joinTo()` and `connectTo()` use relationship metadata and the sub-resource path; inferred relationship behavior remains partial and depends on schema configuration.

`orderBy()`, `orderByAsc()`, `orderByDesc()`, `orderByRaw()`, and `reorder()` control ordering. `limit()`/`take()` and `offset()`/`skip()` set row bounds; [`paginate()`](../../src/framework/Traits/QueryBuilderTrait.php#L912) sets a `LIMIT` and offset using `(page_size * page) - page_size`. When page size is omitted it reads `paginator.default_limit`, falling back to 10. It does not calculate a total row count or return page metadata. Test sources assert offsets for pages 1 and 3, but were not run. `groupBy()`, `having()`, `havingRaw()`, `union()`, and `unionAll()` are present in the trait. The names `oldest()`, `latest()`, and `newest()` do not match their ordinary chronological reading in this checkout: `oldest()` emits descending `created_at`, `latest()` delegates to `oldest()`, and `newest()` emits ascending `created_at`. Test sources assert two of those SQL forms, but were not run. For inferred joins and nested relation loading, see [Relationships, joins, and subresources](relations.md). Do not infer a complete SQL dialect or driver-compatibility matrix from those assertions.

## Read results

- `get()` returns all fetched rows using the selected fetch mode. An empty executed result is `[]`; when execution is disabled or `execute()` returns false, the method returns `false`.
- `first()` returns one row, `[]` when no row is fetched, or `false` when execution is disabled or fails. `firstOrFail()` throws a generic exception for an empty result. `getOne()` and `top()` delegate to `first()`.
- `find($id)` adds a condition and returns the builder; `findOr()` and `findOrFail()` check existence before returning that builder or invoking/throwing from the fallback.
- `value($field)` fetches one scalar, and `pluck($field)` sets column mode and fetches that column. `exists()` compiles an existence query and returns a boolean on its executed path.
- `assoc()`, `asObject()`, and `column()` change the fetch mode. `get(..., $pristine = true)` and `first(..., $pristine = true)` bypass output mutators and transformers; ordinary reads apply them when configured.
- `count()`, `avg()`, `sum()`, `min()`, and `max()` delegate to [`aggregate()`](../../src/framework/Traits/QueryBuilderTrait.php#L2114). The ungrouped path casts the fetched scalar to `int`, including `AVG` and `SUM`; this can discard fractional precision. The grouped path casts the result of `fetchAll()` to `int` instead of providing a verified row collection. No aggregate result was fetched from a database.

## Writes, soft deletes, and execution modes

The trait declares several write paths with different behavior. `create()` prepares one model-backed insert; `insert()` defaults to a transaction wrapper and invokes create hooks; `rawInsert()` delegates to a lower-level insert path without the same hook sequence; `bulkInsert()`, `createOrIgnore()`, `createOrUpdate()`, `insertOrIgnore()`, and `insertOrUpdate()` have separate implementations. These methods are not interchangeable aliases, and their database effects were not run in this audit. See [Database transactions](transactions.md) for the transaction helper and nested behavior.

`update($data)` requires a connection, non-empty associative data, and a non-empty `WHERE`; it applies the configured mutation, fillable, validator, and hook paths before executing. Its result is a row count or `false` on the non-executed return path. `delete()` uses a soft-delete update when the model enables it and the call allows it; the physical delete path requires a condition. `forceDelete()` selects physical deletion. `truncate()` is also exposed and has no row filter; it is intentionally not shown as a usage example.

Soft-delete scope is conditional on the model schema having `deleted_at`. The trait exposes `setSoftDelete()`, `deleted()`, `showDeleted()`, `withTrashed()`, `onlyTrashed()`, `trashed()`, `is_trashed()`, `undelete()`, and `restore()`. Their source paths and SQL assertions have not been exercised against a live database here.

`setExecutionMode()`, `simulate()`, `preview()`, and `normalExecution()` set a mode flag. The [audit finding](../audit/README.md#claim-level-findings-query-builder) shows that `update()` and both delete paths do not honor that flag as a general no-write switch. `$exec` and the execution mode are different controls; `dontExec()` is not a safe offline substitute for inspecting every write method.

## Evidence and scope

`ModelTest`, `QueryBuilderExtendedTest`, `PGSQLQueryBuilderTest`, and `SimpleORMTest` contain SQL assertions or database-oriented fixtures for selected query forms; the files were inspected, not executed. `SimpleORMTest` declares a `test_sqlite` in-memory connection. Normal `DB::table()` construction opens the selected configured connection. The configured [PHPUnit file](../../phpunit.xml) includes `unit-tests/`; no test result is claimed here.

Write operations, transaction behavior, execution-mode safety, raw-query contracts, pagination, aggregates, relation loading, automatic joins, and PostgreSQL compatibility are described at source level only; none is presented as a reproduced database workflow.
